### 1.7 类（class）与面向对象

```python
# 类：将数据和相关操作打包在一起的"蓝图"
# 可以理解为"自定义数据类型"
class Dog:
    # __init__ 是构造函数：创建实例时自动调用
    def __init__(self, name, age):
        # self 指向当前实例本身
        self.name = name    # 实例属性
        self.age = age

    # 实例方法：操作实例数据
    def bark(self):
        return f"{self.name} says Woof!"

    @staticmethod
    def species():
        return "Canis familiaris"

my_dog = Dog("Buddy", 3)

print(my_dog.bark())    # "Buddy says Woof!"

# 继承：子类获得父类的所有属性和方法
class GuideDog(Dog):            # GuideDog 继承 Dog
    def __init__(self, name, age, owner):
        super().__init__(name, age)  # 调用父类的 __init__
        self.owner = owner

    def guide(self):
        return f"{self.name} is guiding {self.owner}"
```

### 1.8 装饰器（Decorator）

装饰器是本项目大量使用的 Python 特性，务必理解：

```python
# 装饰器：在"不修改原函数"的前提下，给函数"添加额外功能"
# 语法：在函数定义上方使用 @装饰器名

# 理解装饰器的简单类比：
# 你有一台收音机（原函数），装饰器就像给收音机套了一个"保护壳"（额外功能）
# 收音机本身的功能不变，但多了一些额外特性（比如防水、防摔）

# 示例：自定义装饰器
def log_execution(func):
    """这个装饰器在函数执行前后打印日志"""
    def wrapper(*args, **kwargs):
        print(f"开始执行: {func.__name__}")
        result = func(*args, **kwargs)    # 调用原函数
        print(f"执行完成: {func.__name__}")
        return result
    return wrapper

# 使用装饰器
@log_execution
def add(a, b):
    return a + b

add(1, 2)
# 输出:
# 开始执行: add
# 执行完成: add

# 本项目中常见的装饰器：
# @tool      → LangChain 工具装饰器，把普通函数变成"智能体可调用的工具"
# @staticmethod → 标记静态方法，不需要实例就能调用
# @abstractmethod → 标记抽象方法，子类必须实现
# @wraps(func) → 保留原函数的元信息（名称、文档字符串等）
```

## 二、大语言模型（LLM）基础

### 2.1 什么是大语言模型（LLM）？

大语言模型（Large Language Model，简称 LLM）是一种 AI 系统，能理解和生成人类语言。你可以把它理解为一个"超级聪明的对话机器人"。

**常见的 LLM 有：**
- **GPT 系列**（OpenAI 公司）：如 GPT-4、GPT-5
- **Claude 系列**（Anthropic 公司）：如 Claude 3.5、Claude 4
- **Gemini 系列**（Google 公司）：如 Gemini Pro、Gemini Flash
- **Grok 系列**（xAI 公司）：如 Grok 4

### 2.2 LLM 的工作方式

```
用户输入（Prompt/提示词）
    │
    ▼
┌─────────────┐
│   LLM 模型   │   ← 通过 API（网络接口）发送请求
└─────────────┘
    │
    ▼
模型输出（Response/响应）
```

**关键概念：**
- **Prompt（提示词）**：你发给 LLM 的文本。就像你向 ChatGPT 提问一样。
- **Response（响应）**：LLM 返回的文本。
- **System Prompt（系统提示词）**：一段特殊的提示词，定义 AI 的"角色"和"行为规范"。
  - 例如："你是一位专业的市场分析师，负责分析技术指标..."
- **API Key（API 密钥）**：一串密码，用于验证你有权使用 LLM 服务。类似一把"钥匙"。
- **Token（令牌）**：LLM 计算费用的单位。大约 1 个中文字 ≈ 2 个 token，1 个英文单词 ≈ 1-2 个 token。

### 2.3 什么是"工具调用"（Function Calling / Tool Calling）？

这是本项目最核心的概念之一。

**问题**：LLM 本身只能"说话"，不能获取实时数据、不能做计算、不能上网搜索。

**解决方案**：工具调用。你事先告诉 LLM："你有这些工具可用"，然后 LLM 在需要时可以"请求"调用某个工具。

```
步骤 1: 你告诉 LLM
  "你可以使用 get_stock_data 工具来获取股票数据"
  "该工具需要参数：symbol（股票代码）、start_date、end_date"

步骤 2: LLM 分析用户的问题，决定是否需要工具
  用户问："分析 AAPL 的市场数据"
  LLM 思考："我需要先获取 AAPL 的价格数据"

步骤 3: LLM 输出"工具调用请求"（tool_call）
  tool_call = {
      "name": "get_stock_data",
      "args": {"symbol": "AAPL", "start_date": "2024-01-01", "end_date": "2024-06-01"}
  }
  （注意：LLM 只是"请求"调用，真正的执行由程序代码完成）

步骤 4: 程序代码执行工具函数，获取数据
  data = get_stock_data("AAPL", "2024-01-01", "2024-06-01")

步骤 5: 将工具结果返回给 LLM
  LLM 看到数据后，生成分析报告
```

### 2.4 什么是"消息"（Message）？

LLM 的对话是通过"消息列表"来管理的：

```python
messages = [
    SystemMessage(content="你是一位市场分析师"),      # 系统消息：定义 AI 角色
    HumanMessage(content="请分析 AAPL 的数据"),       # 人类消息：用户的问题
    AIMessage(content="好的，我来分析..."),            # AI 消息：AI 的回答
    ToolMessage(content="AAPL 收盘价: 150.5"),       # 工具消息：工具返回的数据
]
```

- **SystemMessage**：设定 AI 的角色和行为规范
- **HumanMessage**：用户/人类发送的消息
- **AIMessage**：AI 模型生成的回复
- **ToolMessage**：工具（函数）执行后返回的结果

### 2.5 温度（Temperature）与推理能力

- **温度**：控制 LLM 输出的"随机性"。温度越高，回答越有创造性但可能不够准确；温度越低，回答越确定但可能缺乏多样性。
- **推理能力（Reasoning）**：某些高级 LLM（如 GPT-5、Claude Opus）支持"思考"能力，可以在回答前进行推理。
  - `reasoning_effort`（OpenAI）：low / medium / high
  - `effort`（Anthropic）：low / medium / high
  - `thinking_level`（Google）：minimal / low / high

## 三、LangChain 框架详解

### 3.1 什么是 LangChain？

**问题**：直接调用 LLM API 需要写大量重复代码（发请求、解析响应、管理对话历史等）。

**解决方案**：LangChain 是一个 Python 库，封装了与 LLM 交互的常用操作，让开发者可以更简洁地构建 AI 应用。

**类比**：
- 直接用 LLM API ≈ 手动写信、贴邮票、去邮局寄信
- 用 LangChain ≈ 用电子邮件客户端：输入内容，点击发送，自动处理

### 3.2 LangChain 的核心概念

#### 3.2.1 LLM 实例

LangChain 封装了各供应商的 LLM 调用接口：

```python
# 创建 OpenAI 的 LLM 实例
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="gpt-5-mini",           # 模型名称
    api_key="sk-xxx",             # API 密钥
    base_url="https://api.openai.com/v1",  # API 地址
)

# 调用 LLM
response = llm.invoke("你好，请介绍一下自己")
# response 是一个 AIMessage 对象
# response.content 包含 LLM 返回的文本
print(response.content)  # "你好！我是一个 AI 助手..."
```

#### 3.2.2 提示词模板（PromptTemplate / ChatPromptTemplate）

**问题**：每次调用 LLM 都要手动拼接字符串，不够灵活且容易出错。

**解决方案**：提示词模板——预定义好"骨架"，运行时填入变量：

```python
from langchain_core.prompts import ChatPromptTemplate

# 创建模板：用 {变量名} 占位
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一位{role}，请回答用户的问题。"),
    ("human", "{question}"),
])

# 填充模板变量
filled_prompt = prompt.format(
    role="市场分析师",
    question="分析 AAPL 的趋势"
)

# MessagesPlaceholder：在模板中预留"消息列表"的位置
from langchain_core.prompts import MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一位助手。"),
    MessagesPlaceholder(variable_name="messages"),  # 运行时插入消息列表
])

# partial()：部分填充模板变量（后续再填充其他变量）
prompt = prompt.partial(role="市场分析师")
# 后续可以继续填充其他变量

# 模板的使用流程：
# 创建模板 → partial 填充固定变量 → 运行时填充动态变量 → 发给 LLM
```

#### 3.2.3 工具（Tool）

工具是 LLM 可以"请求调用"的函数。LangChain 用 `@tool` 装饰器将普通函数变成工具：

```python
from langchain_core.tools import tool
from typing import Annotated

# 用 @tool 装饰器定义工具
@tool
def get_stock_data(
    symbol: Annotated[str, "股票代码，如 AAPL"],          # 参数描述
    start_date: Annotated[str, "起始日期，格式 yyyy-mm-dd"],
) -> str:
    """获取指定股票的价格数据"""                              # 这个 docstring 会成为工具描述
    # 实际获取数据的代码
    return "AAPL,2024-01-01,150.5,..."

# @tool 装饰器自动做了什么：
# 1. 函数名 get_stock_data → 工具的 name 属性
# 2. 函数的 docstring → 工具的 description 属性
# 3. Annotated 中的描述文字 → 工具的参数说明
# 4. 参数的类型注解 → 工具的参数 schema

# 这些信息会被发送给 LLM，LLM 据此决定何时调用、传什么参数
```

#### 3.2.4 工具绑定（bind_tools）

将工具"告诉"LLM，让 LLM 知道它可以调用这些工具：

```python
# bind_tools：将工具列表"绑定"到 LLM 实例
llm_with_tools = llm.bind_tools([get_stock_data, get_indicators])

# 调用绑定了工具的 LLM
response = llm_with_tools.invoke("请分析 AAPL 的市场数据")

# LLM 的响应中可能包含 tool_calls：
# response.tool_calls = [
#     {"name": "get_stock_data", "args": {"symbol": "AAPL", "start_date": "2024-01-01"}}
# ]
# 这表示 LLM 想要调用 get_stock_data 工具

# 如果 response.tool_calls 为空列表，说明 LLM 不需要工具，已经给出了最终回答
```

#### 3.2.5 链（Chain）和管道操作符（|）

LangChain 的核心特性是"链"——将多个步骤串联起来：

```python
# | 管道操作符：将前一步的输出作为后一步的输入
# 类比 Unix 管道：cat file | grep "keyword" | sort

# 基本链
chain = prompt | llm
# 等价于：
# 1. prompt.format(...) → 格式化提示词
# 2. llm.invoke(格式化后的提示词) → 调用 LLM

# 带工具的链
chain = prompt | llm.bind_tools(tools)
# 1. prompt.format(...) → 格式化提示词
# 2. llm_with_tools.invoke(格式化后的提示词) → 调用绑定了工具的 LLM

# 执行链
result = chain.invoke(input_data)
```

#### 3.2.6 invoke 方法

`invoke()` 是 LangChain 中"执行"操作的统一方法：

```python
# 对 LLM 执行
response = llm.invoke("你好")              # 发送消息并获取回复

# 对提示词模板执行
prompt = template.invoke({"name": "AAPL"})  # 填充模板变量

# 对链执行
result = chain.invoke(input_data)            # 执行整个链

# 对图执行
final_state = graph.invoke(initial_state)     # 执行整个工作流图
```

### 3.3 LangChain 在本项目中的角色

```
用户代码调用 graph.propagate("AAPL", "2024-01-15")
  │
  ├── LangGraph 编排多个智能体（详见下一节）
  │     │
  │     ├── 智能体 1（市场分析师）
  │     │     ├── LangChain ChatPromptTemplate 格式化提示词

  │     │     ├── LangChain LLM invoke 调用 LLM
  │     │     └── LLM 可能返回 tool_calls
  │     │
  │     ├── 工具节点执行工具调用
  │     │     └── LangChain @tool 装饰的工具函数
  │     │
  │     └── 智能体 2（新闻分析师）...
  │
  └── 返回最终决策
```

## 四、LangGraph 框架详解

### 4.1 什么是 LangGraph？

**问题**：单个 LLM 调用只能做一件事。如果要实现"多个 AI 协作、按顺序执行、互相辩论"这样复杂的工作流，需要自己写大量编排逻辑。

**解决方案**：LangGraph 是 LangChain 团队开发的"工作流编排框架"，将复杂的 AI 协作流程建模为"图"（Graph）。

**类比**：
- LangChain = 让一个 AI 更聪明（工具、记忆、提示词模板）
- LangGraph = 让多个 AI 协作（编排、路由、循环）

### 4.2 图（Graph）的基本概念

```
    ┌──────────┐         ┌──────────┐
    │ 节点 A   │ ──边──▶ │ 节点 B   │
    └──────────┘         └──────────┘
                              │
                         条件边
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
              ┌──────────┐        ┌──────────┐
              │ 节点 C   │        │ 节点 D   │
              └──────────┘        └──────────┘
```

- **节点（Node）**：图中的一个处理步骤。每个节点是一个函数，接收状态、返回状态更新。
- **边（Edge）**：节点之间的连接，表示数据流动方向。
- **条件边（Conditional Edge）**：根据条件决定下一个节点（实现分支和循环）。
- **状态（State）**：在节点间传递的共享数据。所有节点都能读写这个状态。

### 4.3 StateGraph 的工作机制

```python
from langgraph.graph import StateGraph, START, END

# 第 1 步：定义状态类型（TypedDict）
from typing import TypedDict

class MyState(TypedDict):
    messages: list       # 消息列表
    report: str          # 分析报告
    count: int           # 计数器

# 第 2 步：创建图
workflow = StateGraph(MyState)

# 第 3 步：添加节点
# 每个节点是一个函数：接收 state，返回 state 更新
def analyst_node(state):
    # 读取状态
    messages = state["messages"]
    # 执行分析...
    # 返回状态更新（只返回需要更新的字段）
    return {"report": "分析结果...", "messages": [new_message]}

workflow.add_node("analyst", analyst_node)
workflow.add_node("researcher", researcher_node)

# 第 4 步：添加边（定义执行顺序）
# 普通边：A → B（执行完 A 一定执行 B）
workflow.add_edge(START, "analyst")        # 从 START 开始，执行 analyst
workflow.add_edge("analyst", "researcher") # analyst 完成后执行 researcher
workflow.add_edge("researcher", END)       # researcher 完成后结束

# 条件边：根据条件选择下一个节点
def route_function(state):
    if state["count"] < 3:
        return "analyst"    # 轮数不够，回到 analyst 继续
    else:
        return "end"        # 轮数够了，结束

workflow.add_conditional_edges(
    "analyst",              # 从哪个节点出发
    route_function,         # 条件判断函数
    {
        "analyst": "analyst",  # 如果返回 "analyst"，路由到 analyst 节点（循环）
        "end": END,            # 如果返回 "end"，路由到 END
    }
)

# 第 5 步：编译图
# compile() 会验证图结构是否正确，并生成可执行对象
graph = workflow.compile()

# 第 6 步：执行图
# 方式一：invoke（一次性执行完毕）
final_state = graph.invoke({"messages": [...], "report": "", "count": 0})

# 方式二：stream（逐块获取输出，可以看到每个节点的中间结果）
for chunk in graph.stream({"messages": [...], "report": "", "count": 0}):
    # chunk 是每个节点执行后的状态更新
    print(chunk)
```

### 4.4 START 和 END

LangGraph 有两个特殊的内置节点：

- **`START`**：图的入口。第一条边必须从 `START` 出发。执行图时从这里开始。
- **`END`**：图的出口。到达 `END` 时图执行结束。

### 4.5 状态的合并机制（Reducer）

当多个节点更新同一个状态字段时，LangGraph 使用 **reducer（合并器）** 来决定如何合并：

```
节点 A 返回 {"messages": [msg_A]}
节点 B 返回 {"messages": [msg_B]}

默认行为：覆盖（B 的值覆盖 A 的值）
        → state["messages"] = [msg_B]

使用 Annotated 配置 reducer：
        → state["messages"] = [msg_A, msg_B]  （追加而非覆盖）
```

在本项目中，`messages` 字段使用了 `add_messages` reducer，自动追加消息而非覆盖。其他字段（如 `report`）使用默认行为（覆盖）。

### 4.6 ToolNode

`ToolNode` 是 LangGraph 预置的特殊节点，用于自动执行工具调用：

```
分析师节点（LLM）输出 → 包含 tool_calls
  │
  ▼
ToolNode 自动读取 tool_calls
  │
  ├── 调用 get_stock_data("AAPL", ...)
  ├── 调用 get_indicators("AAPL", "macd", ...)
  │
  ▼
将工具返回结果包装为 ToolMessage
  │
  ▼
回到分析师节点（LLM 看到工具结果，继续分析）
```

### 4.7 条件边的路由机制

条件边是 LangGraph 实现循环和分支的关键：

```python
# 条件函数：接收状态，返回一个字符串（路由键）
def should_continue(state):
    last_message = state["messages"][-1]

    # 检查 LLM 是否请求了工具调用
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"       # 有工具调用 → 去工具节点
    else:
        return "next"        # 没有工具调用 → 去下一个节点

# 添加条件边
workflow.add_conditional_edges(
    "analyst",               # 源节点
    should_continue,         # 条件函数
    {
        "tools": "tools_node",    # 返回 "tools" 时 → 执行 tools_node
        "next": "msg_clear",     # 返回 "next" 时 → 执行 msg_clear 节点
    }
)

# 本项目中的两种路由模式：
# 1. 工具路由：LLM 是否需要调用工具？
#    有 tool_calls → 执行工具 → 回到 LLM → 再检查...
#    无 tool_calls → 进入下一个阶段
#
# 2. 辩论轮数路由：辩论是否结束？
#    轮数 < 上限 → 交给对方研究员继续辩论
#    轮数 >= 上限 → 交给研究经理裁决
```

## 五、金融领域知识

### 5.1 股票基础

- **股票代码（Ticker）**：每只股票的唯一标识。如 AAPL=苹果、NVDA=英伟达、TSLA=特斯拉。
- **交易所后缀**：非美股的股票代码可能带后缀。如 0700.HK=腾讯（香港）、7203.T=丰田（东京）。

### 5.2 OHLCV 数据

每只股票每天的数据包含五个关键值：

| 名称 | 英文 | 含义 |
|------|------|------|
| 开盘价 | Open | 当天交易开始时的价格 |
| 最高价 | High | 当天交易时段内的最高价格 |
| 最低价 | Low | 当天交易时段内的最低价格 |
| 收盘价 | Close | 当天交易结束时的价格 |
| 成交量 | Volume | 当天买卖的股票数量 |

### 5.3 技术指标详解

本项目使用以下技术指标来分析股票走势：

#### 移动平均线（SMA / EMA）

- **SMA（简单移动平均）**：过去 N 天收盘价的平均值。
  - `close_50_sma`：50 日均线（中期趋势指标）
  - `close_200_sma`：200 日均线（长期趋势指标）
  - **用法**：价格在均线上方=上涨趋势；价格在均线下方=下跌趋势
  - **金叉**：50 日均线上穿 200 日均线（看涨信号）
  - **死叉**：50 日均线下穿 200 日均线（看跌信号）

- **EMA（指数移动平均）**：与 SMA 类似，但给最近的价格更大的权重，反应更快。
  - `close_10_ema`：10 日指数均线（短期趋势指标）

#### MACD（移动平均线趋同/背离指标）

衡量价格动量的指标，由三部分组成：

| 指标 | 名称 | 含义 |
|------|------|------|
| `macd` | MACD 线 | 12 日 EMA - 26 日 EMA |
| `macds` | 信号线 | MACD 线的 9 日 EMA |
| `macdh` | 柱状图 | MACD 线与信号线的差值 |

- **用法**：MACD 线上穿信号线=买入信号；下穿=卖出信号
- **柱状图**：柱状图由负转正=动量增强

#### RSI（相对强弱指标）

衡量价格超买/超卖程度，范围 0-100：

- `rsi > 70`：超买（可能要回调下跌）
- `rsi < 30`：超卖（可能要反弹上涨）
- `rsi = 50`：中性

#### 布林带（Bollinger Bands）

由三条线组成的价格通道：

| 指标 | 名称 | 含义 |
|------|------|------|
| `boll` | 中轨 | 20 日简单移动平均 |
| `boll_ub` | 上轨 | 中轨 + 2 倍标准差 |
| `boll_lb` | 下轨 | 中轨 - 2 倍标准差 |

- 价格触及上轨：可能超买
- 价格触及下轨：可能超卖
- 通道收窄：波动率降低，可能即将突破

#### ATR（平均真实波幅）

衡量市场波动性的指标：

- `atr` 值越大：市场波动越大
- **用途**：设置止损位、调整仓位大小

#### VWMA（成交量加权移动平均）

将价格和成交量结合的均线：

- 给高成交量的日子更大权重
- 比普通 SMA 更能反映"真实"价格趋势

#### MFI（资金流量指标）

结合价格和成交量的动量指标：

- `mfi > 80`：超买
- `mfi < 20`：超卖

### 5.4 基本面数据

#### 三大财务报表

| 报表 | 名称 | 核心公式 | 说明 |
|------|------|----------|------|
| 资产负债表 | Balance Sheet | 资产 = 负债 + 股东权益 | 公司在某一时刻的"财务照片" |
| 利润表 | Income Statement | 收入 - 费用 = 利润 | 公司一段时间内的"赚钱记录" |
| 现金流量表 | Cash Flow Statement | 现金流入 - 现金流出 = 净现金流 | 公司实际的"现金进出" |

#### 关键财务指标

| 指标 | 英文 | 含义 |
|------|------|------|
| 市盈率 | PE Ratio | 股价 / 每股收益。衡量股票"贵不贵" |
| 市净率 | PB Ratio | 股价 / 每股净资产 |
| 股息率 | Dividend Yield | 每年分红 / 股价 |
| 净资产收益率 | ROE | 净利润 / 股东权益。衡量"赚钱效率" |
| 资产负债率 | Debt to Equity | 总负债 / 股东权益。衡量"欠债多少" |
| 自由现金流 | Free Cash Flow | 经营现金流 - 资本支出。衡量"真金白银" |

### 5.5 内部人交易（Insider Transactions）

公司高管、董事、大股东买卖本公司股票的记录：

- 高管大量买入：可能认为股价被低估（利好信号）
- 高管大量卖出：可能认为股价已高（利空信号）

### 5.6 五级交易评级

本项目最终输出的交易决策分为五个级别：

| 决策 | 含义 | 操作 |
|------|------|------|
| **BUY** | 买入 | 强烈看涨，建议全仓买入 |
| **OVERWEIGHT** | 超配 | 看涨，建议加大仓位 |
| **HOLD** | 持有 | 中性，维持当前仓位 |
| **UNDERWEIGHT** | 低配 | 看跌，建议减仓 |
| **SELL** | 卖出 | 强烈看跌，建议清仓 |

## 六、设计模式基础

### 6.1 工厂模式（Factory Pattern）

**问题**：需要创建多种类型的对象，如果直接在代码中 `if-else` 判断类型并 `new` 对象，代码会很难维护。

**解决方案**：用一个"工厂函数"统一创建对象：

```python
# 工厂函数：根据参数创建不同类型的对象
def create_llm_client(provider, model):
    if provider == "openai":
        return OpenAIClient(model)
    elif provider == "anthropic":
        return AnthropicClient(model)
    elif provider == "google":
        return GoogleClient(model)

# 使用：不需要知道具体类名
client = create_llm_client("openai", "gpt-5-mini")
```

### 6.2 策略模式（Strategy Pattern）

**问题**：同一个功能有多种实现方式，需要在运行时切换。

**解决方案**：将不同实现封装成独立的"策略"，通过配置选择：

```python
# 不同数据源 = 不同策略
strategies = {
    "yfinance": get_yfinance_data,        # Yahoo Finance 策略
    "alpha_vantage": get_alpha_vantage_data,  # Alpha Vantage 策略
}

# 运行时根据配置选择策略
def get_data(strategy_name, *args):
    strategy = strategies[strategy_name]   # 获取策略
    return strategy(*args)                # 执行策略
```

### 6.3 责任链模式（Chain of Responsibility）

**问题**：主数据源可能失败，需要自动降级到备用数据源。

**解决方案**：按顺序尝试每个数据源，失败则尝试下一个：

```python
# 降级链：yfinance → alpha_vantage → ...
for vendor in ["yfinance", "alpha_vantage"]:
    try:
        return vendors[vendor](*args)    # 尝试当前供应商
    except RateLimitError:
        continue                          # 限流了，尝试下一个
raise RuntimeError("所有数据源都失败了")
```

### 6.4 抽象基类（Abstract Base Class, ABC）

**问题**：多个类有相同的接口，需要强制子类实现某些方法。

**解决方案**：定义抽象基类，声明抽象方法，子类必须实现：

```python
from abc import ABC, abstractmethod

class BaseLLMClient(ABC):           # 继承 ABC 表示是抽象基类
    @abstractmethod                  # abstractmethod 表示子类必须实现
    def get_llm(self):
        pass                         # 基类中只定义接口，不实现

    @abstractmethod
    def validate_model(self):
        pass

# 子类必须实现所有抽象方法
class OpenAIClient(BaseLLMClient):
    def get_llm(self):               # 必须实现
        return ChatOpenAI(...)

    def validate_model(self):        # 必须实现
        return model in VALID_MODELS

# 如果子类没有实现抽象方法，实例化时会报错：
# TypeError: Can't instantiate abstract class
```

### 6.5 闭包与工厂函数

**问题**：需要创建一个"可配置的函数"。

**解决方案**：外部函数创建内部函数，内部函数引用外部变量：

```python
# 外部函数是"工厂"，生产配置好的内部函数
def create_msg_delete():
    # 内部函数（闭包）引用了外部函数的作用域
    def delete_messages(state):
        messages = state["messages"]
        return {"messages": [RemoveMessage(id=m.id) for m in messages]}

    return delete_messages   # 返回内部函数

# 使用
delete_func = create_msg_delete()   # 生产一个删除函数
result = delete_func(state)         # 调用它
```


### 7.2 完整工作流程

当用户调用 `graph.propagate("NVDA", "2024-05-10")` 时，系统执行以下流程：

```
阶段 1: 分析师团队（4 位分析师依次执行）
  ┌─ 市场分析师 ──────────────────────────────────────┐
  │ 1. LLM 决定需要哪些数据 → 请求调用 get_stock_data │
  │ 2. ToolNode 执行 → 返回价格数据                    │
  │ 3. LLM 看到数据 → 请求调用 get_indicators          │
  │ 4. ToolNode 执行 → 返回技术指标                    │
  │ 5. LLM 综合分析 → 生成市场分析报告                  │
  │ 6. 清除消息历史（为下一个分析师准备干净的上下文）      │
  └──────────────────────────────────────────────────┘
  ↓
  社交媒体分析师 → 新闻分析师 → 基本面分析师（同样流程）
  ↓

阶段 2: 研究员辩论（多空双方交替辩论）
  ┌─ 多头研究员 ──────────────────────────────────────┐
  │ 阅读所有分析报告 → 从看涨角度论证 → 更新辩论历史      │
  └──────────────────────────────────────────────────┘
  ↓
  ┌─ 空头研究员 ──────────────────────────────────────┐
  │ 阅读所有分析报告 → 从看跌角度反驳 → 更新辩论历史      │
  └──────────────────────────────────────────────────┘
  ↓
  （循环 max_debate_rounds 轮）
  ↓
  ┌─ 研究经理 ────────────────────────────────────────┐
  │ 综合多空双方观点 → 做出投资判断                      │
  └──────────────────────────────────────────────────┘
  ↓

阶段 3: 交易决策
  ┌─ 交易员 ──────────────────────────────────────────┐
  │ 根据研究经理的判断 → 制定具体交易计划（买入/卖出/持有）│
  └──────────────────────────────────────────────────┘
  ↓

阶段 4: 风险管理辩论（三方辩论）
  ┌─ 激进分析师 ──────────────────────────────────────┐
  │ 从高风险高回报角度评估 → 发表观点                     │
  └──────────────────────────────────────────────────┘
  ↓
  保守分析师 → 中性分析师 → 激进分析师 → ...（循环）
  ↓
  ┌─ 投资组合经理 ────────────────────────────────────┐
  │ 综合三方风险观点 → 做出最终交易决策                   │
  └──────────────────────────────────────────────────┘
  ↓

阶段 5: 信号处理
  ┌─ 信号处理器 ──────────────────────────────────────┐
  │ 从最终决策文本中提取简洁评级：BUY / HOLD / SELL       │
  └──────────────────────────────────────────────────┘
```

### 7.3 状态流转

所有智能体共享一个 `AgentState` 状态字典，随着工作流推进，状态逐步丰富：

```
初始状态:
  { ticker: "NVDA", trade_date: "2024-05-10", messages: [...] }

→ 市场分析师执行后:
  { ..., market_report: "市场分析报告..." }

→ 新闻分析师执行后:
  { ..., news_report: "新闻分析报告..." }

→ 所有分析师完成后:
  { ..., market_report, sentiment_report, news_report, fundamentals_report }

→ 多空辩论后:
  { ..., investment_debate_state: { bull_history, bear_history, judge_decision } }

→ 交易员执行后:
  { ..., trader_investment_plan: "交易计划..." }

→ 风险辩论后:
  { ..., risk_debate_state: { aggressive_history, ... } }

→ 最终:
  { ..., final_trade_decision: "最终决策文本..." }
```

### 7.4 数据获取流程

当智能体需要数据时，通过工具调用获取：

```
智能体请求调用工具 get_stock_data("NVDA", "2024-01-01", "2024-05-10")
  │
  ▼
@tool 装饰的 get_stock_data 函数
  │
  ▼
route_to_vendor("get_stock_data", "NVDA", "2024-01-01", "2024-05-10")
  │
  ├── 检查 tool_vendors 配置（工具级别优先）
  ├── 检查 data_vendors 配置（类别级别）
  │
  ├── 如果配置为 "yfinance" → 调用 y_finance.py 中的函数
  │     └── Yahoo Finance API → 返回 CSV 数据
  │
  ├── 如果配置为 "alpha_vantage" → 调用 alpha_vantage_stock.py 中的函数
  │     └── Alpha Vantage API → 返回 CSV 数据
  │
  └── 如果主数据源失败（如限流）→ 自动降级到备用数据源
  │
  ▼
返回数据给智能体
```

### 7.5 反思与记忆机制

系统可以"从经验中学习"：

```
分析完成后:
  graph.propagate("NVDA", "2024-05-10")  →  得出决策 "BUY"

一段时间后:
  graph.reflect_and_remember(returns_losses=500)
  │
  ├── 反思多头研究员: "我的看多分析是否准确？"
  ├── 反思空头研究员: "我的看空分析是否有遗漏？"
  ├── 反思交易员: "交易计划是否合理？"
  ├── 反思研究经理: "裁决是否公正？"
  ├── 反思投资组合经理: "风险管理是否到位？"
  │
  ▼
每个角色的反思结果存入各自的 FinancialSituationMemory
  │
  ▼
下次分析时:
  研究员会从记忆中检索相似的历史经验
  避免重蹈覆辙，做出更明智的决策
```
